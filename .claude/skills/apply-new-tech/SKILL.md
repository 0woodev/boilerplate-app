## 작업 순서

### 1. 현재 프로젝트 구조 파악

이 레포는 `be/`(Python Lambda)와 `fe/`(React/Vite)를 서브모듈로 가진 오케스트레이터다.

아래를 확인한다:

- `be/requirements.txt` — 백엔드 의존성
- `fe/package.json` — 프론트엔드 의존성
- `be/CLAUDE.md` / `fe/CLAUDE.md` — 현재 진행 현황
- `be/terraform/` 구조 — 인프라 현황 (Lambda, DynamoDB, API Gateway)

핵심 확인 포인트:
- 도입 대상이 **BE에만**, **FE에만**, 또는 **양쪽 모두**에 영향을 주는가?
- 인프라 변경(Terraform)이 수반되는가?
- GitHub Actions CI/CD 파이프라인 변경이 필요한가?
- dev / prod 스테이지 분리 방식과 충돌하는가?

### 2. 도입 방법 탐색

웹 검색 또는 지식 기반으로 다음을 조사한다:

- 공식 문서 확인 (설치, 기본 설정)
- AWS 서버리스 환경(Lambda, API Gateway)과의 통합 패턴 (BE 관련 시)
- React/Vite 환경과의 통합 패턴 (FE 관련 시)
- 대안 기술 목록 (최소 2~3개 옵션)
- 실제 사용 사례 및 트레이드오프

### 3. 도입 방법 비교

아래 기준으로 옵션을 비교한다:

| 기준 | 설명 |
|---|---|
| 영향 범위 | BE만 / FE만 / 인프라 / 전체 |
| 복잡도 | 도입·유지보수 난이도 |
| 비용 | 추가 AWS 리소스 or 서드파티 비용 |
| CI/CD 영향 | GitHub Actions 변경 필요 여부 |
| 확장성 | 기존 구조 변경 없이 확장 가능한가 |

### 4. 추천 방향 결정

비교 결과를 바탕으로 **가장 적합한 방법 1개를 추천**한다.

추천 이유:
- 이 프로젝트 구조(서버리스 + SPA)에 맞는 이유
- 장·단점 요약
- 리스크 및 주의사항

### 5. 구체적 실행 계획 제시

```
STEP 1. 변경 대상 확인 (be/ / fe/ / terraform/ / .github/)

STEP 2. 패키지/모듈 설치

STEP 3. 설정 파일 생성 위치 및 내용

STEP 4. 첫 사용 예시 코드

STEP 5. Terraform 변경이 필요하다면 변경 내용

STEP 6. GitHub Actions 변경이 필요하다면 변경 내용

STEP 7. 검증 방법 (로컬 + dev 배포 후 확인)
```

실제 코드 스니펫을 최대한 포함한다.

### 6. CLAUDE.md 업데이트 제안

be/, fe/ 중 해당하는 곳의 `CLAUDE.md`에 추가할 항목을 제안한다:

```markdown
- [ ] **{기술명} 도입** — {한 줄 설명}
```

## 출력 형식

1. **현재 구조 요약** — 기술 도입 전 상태 (BE/FE/인프라 각각)
2. **도입 옵션 비교표**
3. **추천 방향 + 이유**
4. **실행 계획 (단계별 코드 포함)**
5. **CLAUDE.md 업데이트 제안**
